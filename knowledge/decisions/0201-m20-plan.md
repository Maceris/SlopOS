Status: accepted

M20

## Context
With M19 and its catch-up built, what's left on the roadmap is its *Later* list: real hardware's devices, indexing
and live queries, a POSIX personality and ABI v1; and what M19 deferred, RISC-V's hardware debugging and an IMSIC in
groups. The owner chose, on 2026-11-27, to plan it all as one milestone, its design settled first, then built stage by
stage, committed after each, with the questions that come up kept for the end.

## Settled with the owner (2026-11-27)
- **ABI v1 is declared at M20's end**: the comparison tooling first, every surface reviewed once the other stages
  have added what they need, then v1 as the last stage (`0027`'s own decision, made here).
- **USB**: keyboards and mice (HID boot protocol), mass storage (bulk-only, SCSI), and hubs.
- **Indexes live in the volume server**, updated in the transaction that changes the file; a query runs beneath a
  directory handle and sees only what it reaches; a live query is a channel of changes.
- **A small libc**, written in Hemera, for porting C tools: Hemera gains C-callable exports, a general feature, and
  ported C is compiled by a stock clang as freestanding ELF with SlopOS's headers. Nothing in Hemera is SlopOS's alone:
  no C compiler built for SlopOS, Hemera's LLVM unchanged.
- **Both of M19's deferrals**: RISC-V's debug triggers and an IMSIC in groups.
- **Left out**: forgetting a volume's key on suspend (`lessons.md` §10.3), as there's no suspend; real machines
  themselves, as every device here is tested on QEMU, on all three architectures where QEMU has it.

## Decision: the stages
- **20a, the ABI comparison.** A tool that reads the ABI package (`std/os/slop_os`) and writes what it declares,
  each system call's number and signature, each layout's fields, offsets and sizes, each enum's values, as a
  canonical description; and compares two, saying every change that 0025's rules forbid after v1 (a number reused or
  a signature changed in place, a layout changed but for growing a size-prefixed struct, a value renumbered).
  Checked in Hemera's build packages' compile-time code, which reads declarations already. A Build or boot test
  compares against a description kept in the repository, which is updated on purpose until v1.
- **20b, NVMe.** A user-space driver: the controller's admin queue, one I/O queue pair per CPU it's given, MSI-X, its
  DMA through the IOMMU, namespaces as block devices the storage manager takes as it does virtio-blk's. Tested with
  QEMU's `nvme` on all three: a volume on it, read and written, survives a restart of the driver.
- **20c, AHCI.** A user-space driver for SATA disks behind an AHCI controller (QEMU's `ich9-ahci`, q35's own on
  x86-64): its ports, command lists and FIS, NCQ where the disk has it, MSI. Tested as NVMe is.
- **20d, xHCI and hubs.** A user-space driver for the host controller: its rings (command, event, transfer), slots
  and endpoints, enumeration on the root ports and through hubs (the hub class's port control), a device's
  descriptors read and handed to a class driver over a typed protocol, each device's endpoints its own. QEMU's
  `qemu-xhci` with `usb-hub`.
- **20e, USB keyboards and mice.** The HID class driver, boot protocol (keyboard and mouse reports), feeding the input
  service as virtio-input does, so the console and the GUI take them. `usb-kbd`, `usb-mouse` and `usb-tablet`.
- **20f, USB mass storage.** Bulk-only transport and SCSI's few commands (inquiry, capacity, read, write), a block
  device the storage manager takes; a stick's FAT read by a FAT server that's untrusted, as every FAT server is, its
  parser fuzzed with malformed volumes. `usb-storage`.
- **20g, RISC-V's debug triggers.** The SBI's debug triggers extension (DBTR): hardware breakpoints, watchpoints and a
  single step for `set_debug`, so `test_control`'s debugger test and the debugger's tests run on RISC-V. Where the
  firmware has no DBTR, as before, the tests say so.
- **20h, an IMSIC in groups.** Every `reg` range of an IMSIC and its group and hart index bits, so each hart's file
  is found on a multi-socket board; the doorbell and MRIFs follow. QEMU `virt` with several sockets.
- **20i, indexes.** A volume's indexes declared by schema and field (a typed file's value's field), kept by its
  volume server in its B+tree, each entry the field's value and the file; updated in the transaction that writes the
  file, so an index never disagrees with what it indexes; built at declaration from what's there.
- **20j, queries and live queries.** A query: a typed predicate over indexed fields (comparisons, and, or, not)
  beneath a directory handle, answering the files it reaches, as names relative to the handle; one that can't use an
  index scans. A live query is a channel answering the matches first, then each one added, changed or gone as
  transactions commit. In `std` as a typed API; in the shell as `query`, its results a table like any program's.
- **20k, C-callable exports in Hemera.** A function marked `#export #calling_convention(.c)`, without `#no_context`, is
  called from C as a C function: the compiler gives it an entry that saves the C caller's value of the carrier
  register, finds the carrier in the thread's thread-local storage, where the runtime keeps it, and puts the caller's
  value back on return. Only functions so marked get it; nothing else is reachable from C, nor pays for it. Hemera's
  tests on Windows, Linux and freestanding: C calling back into Hemera (`qsort`'s comparator, a C library's callback).
- **20l, the libc.** A C library over SlopOS's native capabilities, written in Hemera on 20k: `stdio`, `string`,
  `stdlib`, `ctype`, `math`, `time`, `errno`, and file descriptors for files and directories beneath the handles the
  program was given and for sockets through the network service; no `fork`, signals, or global filesystem. Its
  headers, and a start-up that runs `main` with the program's arguments. Proven by porting Lua and zlib's `minigzip`,
  compiled with a stock clang as freestanding ELF for each architecture and linked by Hemera into SlopOS programs.
- **20m, a review**, of 20a to 20l, as each milestone's.
- **20n, ABI v1.** Every surface in `system-abi.md` §1 reviewed, what's wrong changed, then v1 declared: the version
  in the startup block, the description from 20a kept as v1's, and the comparison failing any change 0025 forbids from
  then on. Its own decision record, as 0027 says.

## Alternatives considered
- **A clang built with Hemera's patches**, compiling C with the carrier register reserved: no shim, but Hemera's LLVM
  would build a C compiler for SlopOS's sake.
- **No libc**: native software only, as §16 leans; kept as the fallback if 20k proves costly.
- **An indexer service**: a simpler volume server, but indexes lagging what they index, and a service reading every
  volume.
- **ABI v1 left for later**: everything here could still change freely, but the comparison would guard nothing.

## Consequences
- SlopOS drives the disks and USB devices a PC has, on QEMU; booting a real machine is a later step.
- Hemera can be called from C on every OS, for the functions that say so.
- From 20n, system calls are append-only and layouts grow only as 0025 allows.

## As Built: 20a, the ABI comparison (2026-11-27)
- **`src/tools/abi_description`**, a hosted tool whose description of the ABI package is a constant worked out when
  it's compiled, from `compiler.package_info` and each type's `type_info_of`: a line for each system call (its number,
  name and signature, `Syscalls`' members in order), each integer, bool or enum constant, and each struct, enum, union
  and alias the package declares or reaches, with each field's offset and type, each member's value and each variant's
  types' offsets. 914 lines now: 99 calls, 157 constants and 28 structs among the types.
- **`--compare`** reads two descriptions as sets of lines keyed by what each names, and says each difference: a call,
  constant or type gone, a call's signature, a member's value or a layout changed are forbidden; a call appended, a new
  constant, type or member, and a struct with a `size` field growing past its fields are allowed. `--exact` fails on
  any difference, as before v1. Checked on edited copies: a call removed, appended, a member renumbered, and the
  startup block grown.
- **`docs/specs/abi_description.txt`** is the description as it's meant to be, which `tools/unit_tests.py` compares
  the built one with, exactly, as one more test; a change to the ABI writes it again (`abi_description --write`).

## As Built: 20b, NVMe (2026-11-27)
- **`src/drivers/nvme`**, a user-space driver started by the supervisor for any device of class 0x010802, serving
  `block.Block` as virtio-blk's driver does, so the storage manager takes its namespace unchanged. The admin queues are
  polled while it starts (identify controller and namespace, create the I/O queues); then one I/O completion and
  submission queue pair of 64 entries, its completions on MSI-X entry 0. Sixteen slots, each a command ID with its
  own PRP list and a 64 KiB buffer; a volatile write cache, where identify says there is one, is flushed on a
  client's flush. Namespaces with blocks bigger than 512 bytes are served in 512-byte blocks.
- **One I/O queue pair, not one per CPU**: the driver is one thread, and a queue per CPU would only pay off with a
  thread per queue. The plan's "per CPU" waits for a driver that's given more than one.
- **`pci`** gains MSI-X (`find_msix`, `set_msix_entry`, `enable_msix`); **`driver_kit.before_device_write`** orders
  memory writes before a doorbell's (`fence rw,ow` on RISC-V, `dmb oshst` on AArch64), which virtio's notify lacked
  too and now uses.
- **`boot.py --disk-bus=nvme`** attaches `--disk` or `--boot-disk` through QEMU's `nvme`; the boot test "boots from a
  disk on an NVMe controller" boots from it, a volume read and written, on all three. A restart of the driver wasn't
  tested separately: the supervisor restarts it as it does virtio-blk's.

## As Built: 20c, AHCI (2026-11-27)
- **`src/drivers/ahci`**, a user-space driver started by the supervisor for any device of class 0x010601, serving
  `block.Block` as NVMe's does. It takes the controller from the firmware (BIOS handoff, where it has it), resets it,
  and starts the first implemented port whose link is up and whose device says it's ATA, passing over an ATAPI drive;
  IDENTIFY DEVICE gives its 48-bit size, its logical sector (served as 512-byte blocks, as NVMe's larger ones are),
  its write cache, and whether it queues. Its interrupt is one MSI, which `pci.enable_msi` sets up.
- **NCQ where both the controller and the disk have it**, to the disk's depth, else READ and WRITE DMA EXT one at a
  time. FLUSH CACHE EXT isn't queued and can't run beside queued commands, so a request that can't go with what's in
  flight waits, in order, and holds back everything after it. Each slot's data is one PRD entry, as a buffer is
  contiguous to the device. An error fails what was in flight and starts the port again, with a COMRESET if the disk
  is still busy.
- **One disk per controller**, the first, as NVMe serves its first namespace; a controller's other disks wait for a
  driver that serves several.
- **A controller with no disk** (x86-64's q35 always has one, holding only the CD) serves a disk of no blocks, and the
  storage manager now asks each disk's size before giving it a partition server, passing over one of none, so disks
  are still numbered as before.
- **System records** hold 64 services and 448 parameters now (magic `SLOPSYS3`), as AHCI's service overflowed 320.
- **Tests**: "boots from a disk on an AHCI controller", q35's own controller on x86-64 and an `ich9-ahci` on RISC-V's
  virt, with its reads and writes queued; and "reads and writes a disk on an AHCI controller", the disk check through
  it, on all three. AArch64's edk2 has no AHCI driver, so it doesn't boot from one there.

## As Built: 20d, xHCI and hubs (2026-11-27)
- **`src/drivers/xhci`**, a user-space driver started by the supervisor for any device of class 0x0c0330. It takes the
  controller from the firmware (USB Legacy Support), resets it, gives it its DCBAA, a command ring, one event ring
  segment and any scratchpads, and its interrupter's MSI-X (MSI where there's no MSI-X). Its root ports are reset where
  they're USB 2's, from the Supported Protocol capability, and each device found is addressed (Enable Slot, Address
  Device), its default endpoint's packet size evaluated from its device descriptor, its configuration read, its first
  alternate settings' bulk and interrupt endpoints added (Configure Endpoint) and its configuration set. Commands and
  the driver's own control transfers are waited for, polled, the events meanwhile handled as they come.
- **Hubs are the driver's own**: their descriptor read, their slot marked a hub with its ports, their ports powered,
  reset and watched through their status change endpoint, and the devices behind them addressed with their route
  strings, a full or low speed one behind a high-speed hub through its transaction translator; at most 5 tiers.
- **Two protocols.** `usb_device` serves one interface to its class driver: Describe (its IDs, speed, class, and its
  endpoints), Control on the default endpoint (SET_ADDRESS, SET_CONFIGURATION and SET_INTERFACE refused, and
  requests only to the interface, its endpoints, or the device's descriptors and status), Transfer on its bulk and
  interrupt endpoints, one in flight on each, ResetEndpoint, and a buffer of its own as the block protocol's. A
  transfer crossing a 64 KiB boundary is two chained TRBs. `usb_bus` is what the driver tells the supervisor: each
  interface Attached, with a connection to it, then Settled once what was there at start is told, and Detached.
- **The supervisor** waits, after the boot set's drivers, for each host controller's Settled (10 s at most), keeping
  each interface and its connection; 20e starts class drivers for them. Until then it logs each as having none.
- **20c's empty controller, fixed**: on x86-64, q35's AHCI controller with only its CD made the supervisor start a
  storage manager with no disks, and a diskless boot degraded. The supervisor now asks each disk's driver its size
  first, giving the storage manager only disks with blocks, and starting none without one; the disk check also skips
  its partition test when the storage manager has no partitions. x86-64's boots start 9 services where AArch64's and
  RISC-V's start 8, the AHCI driver among them, and the root task has 108 grants with the three new drivers.
- **Test**: "finds USB devices on root ports and behind a hub", `qemu-xhci` with `usb-kbd`, `usb-hub` with `usb-mouse`
  behind it, and `usb-tablet`, on all three: each device's interface logged and Attached.
- **Kept for the end**: devices plugged in after start are addressed and Attached, but the input service and the
  storage manager take their devices only as they start, so one that comes later isn't given to them.
