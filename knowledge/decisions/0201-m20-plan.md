# 0201: M20, the Rest of the Roadmap, Planned

Status: accepted
Date: 2026-11-27
Related: `0025` and `0027` (the ABI), `0046` and `0085` (storage), `0038` (no C callbacks, until now), `0199` (M19,
what it deferred), `0200` (before ABI v1), `../problems-and-directions.md` §16 (POSIX), `../design/system-abi.md`,
`../roadmap.md`
M20

## Context
With M19 and its catch-up built, what's left on the roadmap is its *Later* list: real hardware's devices, indexing
and live queries, a POSIX personality and ABI v1; and what M19 deferred, RISC-V's hardware debugging and an IMSIC in
groups. The owner chose, on 2026-11-27, to plan it all as one milestone, its design settled first, then built stage by
stage, committed after each, with the questions that come up kept for the end.

## Settled with the owner (2026-11-27)
- **ABI v1 is declared at M20's end**: the comparison tooling first, every surface reviewed once the other stages
  have added what they need, then v1 as the last stage (`0027`'s own decision, made here).
- **USB**: keyboards and mice (HID boot protocol), mass storage (bulk-only, SCSI), and hubs.
- **Indexes live in the volume server**, updated in the transaction that changes the file; a query runs beneath a
  directory handle and sees only what it reaches; a live query is a channel of changes.
- **A small libc**, written in Hemera, for porting C tools: Hemera gains C-callable exports, a general feature, and
  ported C is compiled by a stock clang as freestanding ELF with SlopOS's headers. Nothing in Hemera is SlopOS's alone:
  no C compiler built for SlopOS, Hemera's LLVM unchanged.
- **Both of M19's deferrals**: RISC-V's debug triggers and an IMSIC in groups.
- **Left out**: forgetting a volume's key on suspend (`lessons.md` §10.3), as there's no suspend; real machines
  themselves, as every device here is tested on QEMU, on all three architectures where QEMU has it.

## Decision: the stages
- **20a, the ABI comparison.** A tool that reads the ABI package (`std/os/slop_os`) and writes what it declares,
  each system call's number and signature, each layout's fields, offsets and sizes, each enum's values, as a
  canonical description; and compares two, saying every change that 0025's rules forbid after v1 (a number reused or
  a signature changed in place, a layout changed but for growing a size-prefixed struct, a value renumbered).
  Checked in Hemera's build packages' compile-time code, which reads declarations already. A Build or boot test
  compares against a description kept in the repository, which is updated on purpose until v1.
- **20b, NVMe.** A user-space driver: the controller's admin queue, one I/O queue pair per CPU it's given, MSI-X, its
  DMA through the IOMMU, namespaces as block devices the storage manager takes as it does virtio-blk's. Tested with
  QEMU's `nvme` on all three: a volume on it, read and written, survives a restart of the driver.
- **20c, AHCI.** A user-space driver for SATA disks behind an AHCI controller (QEMU's `ich9-ahci`, q35's own on
  x86-64): its ports, command lists and FIS, NCQ where the disk has it, MSI. Tested as NVMe is.
- **20d, xHCI and hubs.** A user-space driver for the host controller: its rings (command, event, transfer), slots
  and endpoints, enumeration on the root ports and through hubs (the hub class's port control), a device's
  descriptors read and handed to a class driver over a typed protocol, each device's endpoints its own. QEMU's
  `qemu-xhci` with `usb-hub`.
- **20e, USB keyboards and mice.** The HID class driver, boot protocol (keyboard and mouse reports), feeding the input
  service as virtio-input does, so the console and the GUI take them. `usb-kbd`, `usb-mouse` and `usb-tablet`.
- **20f, USB mass storage.** Bulk-only transport and SCSI's few commands (inquiry, capacity, read, write), a block
  device the storage manager takes; a stick's FAT read by a FAT server that's untrusted, as every FAT server is, its
  parser fuzzed with malformed volumes. `usb-storage`.
- **20g, RISC-V's debug triggers.** The SBI's debug triggers extension (DBTR): hardware breakpoints, watchpoints and a
  single step for `set_debug`, so `test_control`'s debugger test and the debugger's tests run on RISC-V. Where the
  firmware has no DBTR, as before, the tests say so.
- **20h, an IMSIC in groups.** Every `reg` range of an IMSIC and its group and hart index bits, so each hart's file
  is found on a multi-socket board; the doorbell and MRIFs follow. QEMU `virt` with several sockets.
- **20i, indexes.** A volume's indexes declared by schema and field (a typed file's value's field), kept by its
  volume server in its B+tree, each entry the field's value and the file; updated in the transaction that writes the
  file, so an index never disagrees with what it indexes; built at declaration from what's there.
- **20j, queries and live queries.** A query: a typed predicate over indexed fields (comparisons, and, or, not)
  beneath a directory handle, answering the files it reaches, as names relative to the handle; one that can't use an
  index scans. A live query is a channel answering the matches first, then each one added, changed or gone as
  transactions commit. In `std` as a typed API; in the shell as `query`, its results a table like any program's.
- **20k, C-callable exports in Hemera.** A function marked `#export #calling_convention(.c)`, without `#no_context`, is
  called from C as a C function: the compiler gives it an entry that saves the C caller's value of the carrier
  register, finds the carrier in the thread's thread-local storage, where the runtime keeps it, and puts the caller's
  value back on return. Only functions so marked get it; nothing else is reachable from C, nor pays for it. Hemera's
  tests on Windows, Linux and freestanding: C calling back into Hemera (`qsort`'s comparator, a C library's callback).
- **20l, the libc.** A C library over SlopOS's native capabilities, written in Hemera on 20k: `stdio`, `string`,
  `stdlib`, `ctype`, `math`, `time`, `errno`, and file descriptors for files and directories beneath the handles the
  program was given and for sockets through the network service; no `fork`, signals, or global filesystem. Its
  headers, and a start-up that runs `main` with the program's arguments. Proven by porting Lua and zlib's `minigzip`,
  compiled with a stock clang as freestanding ELF for each architecture and linked by Hemera into SlopOS programs.
- **20m, a review**, of 20a to 20l, as each milestone's.
- **20n, ABI v1.** Every surface in `system-abi.md` §1 reviewed, what's wrong changed, then v1 declared: the version
  in the startup block, the description from 20a kept as v1's, and the comparison failing any change 0025 forbids from
  then on. Its own decision record, as 0027 says.

## Alternatives considered
- **A clang built with Hemera's patches**, compiling C with the carrier register reserved: no shim, but Hemera's LLVM
  would build a C compiler for SlopOS's sake.
- **No libc**: native software only, as §16 leans; kept as the fallback if 20k proves costly.
- **An indexer service**: a simpler volume server, but indexes lagging what they index, and a service reading every
  volume.
- **ABI v1 left for later**: everything here could still change freely, but the comparison would guard nothing.

## Consequences
- SlopOS drives the disks and USB devices a PC has, on QEMU; booting a real machine is a later step.
- Hemera can be called from C on every OS, for the functions that say so.
- From 20n, system calls are append-only and layouts grow only as 0025 allows.

## As Built: 20a, the ABI comparison (2026-11-27)
- **`src/tools/abi_description`**, a hosted tool whose description of the ABI package is a constant worked out when
  it's compiled, from `compiler.package_info` and each type's `type_info_of`: a line for each system call (its number,
  name and signature, `Syscalls`' members in order), each integer, bool or enum constant, and each struct, enum, union
  and alias the package declares or reaches, with each field's offset and type, each member's value and each variant's
  types' offsets. 914 lines now: 99 calls, 157 constants and 28 structs among the types.
- **`--compare`** reads two descriptions as sets of lines keyed by what each names, and says each difference: a call,
  constant or type gone, a call's signature, a member's value or a layout changed are forbidden; a call appended, a new
  constant, type or member, and a struct with a `size` field growing past its fields are allowed. `--exact` fails on
  any difference, as before v1. Checked on edited copies: a call removed, appended, a member renumbered, and the
  startup block grown.
- **`docs/specs/abi_description.txt`** is the description as it's meant to be, which `tools/unit_tests.py` compares
  the built one with, exactly, as one more test; a change to the ABI writes it again (`abi_description --write`).

## As Built: 20b, NVMe (2026-11-27)
- **`src/drivers/nvme`**, a user-space driver started by the supervisor for any device of class 0x010802, serving
  `block.Block` as virtio-blk's driver does, so the storage manager takes its namespace unchanged. The admin queues are
  polled while it starts (identify controller and namespace, create the I/O queues); then one I/O completion and
  submission queue pair of 64 entries, its completions on MSI-X entry 0. Sixteen slots, each a command ID with its
  own PRP list and a 64 KiB buffer; a volatile write cache, where identify says there is one, is flushed on a
  client's flush. Namespaces with blocks bigger than 512 bytes are served in 512-byte blocks.
- **One I/O queue pair, not one per CPU**: the driver is one thread, and a queue per CPU would only pay off with a
  thread per queue. The plan's "per CPU" waits for a driver that's given more than one.
- **`pci`** gains MSI-X (`find_msix`, `set_msix_entry`, `enable_msix`); **`driver_kit.before_device_write`** orders
  memory writes before a doorbell's (`fence rw,ow` on RISC-V, `dmb oshst` on AArch64), which virtio's notify lacked
  too and now uses.
- **`boot.py --disk-bus=nvme`** attaches `--disk` or `--boot-disk` through QEMU's `nvme`; the boot test "boots from a
  disk on an NVMe controller" boots from it, a volume read and written, on all three. A restart of the driver wasn't
  tested separately: the supervisor restarts it as it does virtio-blk's.

## As Built: 20c, AHCI (2026-11-27)
- **`src/drivers/ahci`**, a user-space driver started by the supervisor for any device of class 0x010601, serving
  `block.Block` as NVMe's does. It takes the controller from the firmware (BIOS handoff, where it has it), resets it,
  and starts the first implemented port whose link is up and whose device says it's ATA, passing over an ATAPI drive;
  IDENTIFY DEVICE gives its 48-bit size, its logical sector (served as 512-byte blocks, as NVMe's larger ones are),
  its write cache, and whether it queues. Its interrupt is one MSI, which `pci.enable_msi` sets up.
- **NCQ where both the controller and the disk have it**, to the disk's depth, else READ and WRITE DMA EXT one at a
  time. FLUSH CACHE EXT isn't queued and can't run beside queued commands, so a request that can't go with what's in
  flight waits, in order, and holds back everything after it. Each slot's data is one PRD entry, as a buffer is
  contiguous to the device. An error fails what was in flight and starts the port again, with a COMRESET if the disk
  is still busy.
- **One disk per controller**, the first, as NVMe serves its first namespace; a controller's other disks wait for a
  driver that serves several.
- **A controller with no disk** (x86-64's q35 always has one, holding only the CD) serves a disk of no blocks, and the
  storage manager now asks each disk's size before giving it a partition server, passing over one of none, so disks
  are still numbered as before.
- **System records** hold 64 services and 448 parameters now (magic `SLOPSYS3`), as AHCI's service overflowed 320.
- **Tests**: "boots from a disk on an AHCI controller", q35's own controller on x86-64 and an `ich9-ahci` on RISC-V's
  virt, with its reads and writes queued; and "reads and writes a disk on an AHCI controller", the disk check through
  it, on all three. AArch64's edk2 has no AHCI driver, so it doesn't boot from one there.

## As Built: 20d, xHCI and hubs (2026-11-27)
- **`src/drivers/xhci`**, a user-space driver started by the supervisor for any device of class 0x0c0330. It takes the
  controller from the firmware (USB Legacy Support), resets it, gives it its DCBAA, a command ring, one event ring
  segment and any scratchpads, and its interrupter's MSI-X (MSI where there's no MSI-X). Its root ports are reset where
  they're USB 2's, from the Supported Protocol capability, and each device found is addressed (Enable Slot, Address
  Device), its default endpoint's packet size evaluated from its device descriptor, its configuration read, its first
  alternate settings' bulk and interrupt endpoints added (Configure Endpoint) and its configuration set. Commands and
  the driver's own control transfers are waited for, polled, the events meanwhile handled as they come.
- **Hubs are the driver's own**: their descriptor read, their slot marked a hub with its ports, their ports powered,
  reset and watched through their status change endpoint, and the devices behind them addressed with their route
  strings, a full or low speed one behind a high-speed hub through its transaction translator; at most 5 tiers.
- **Two protocols.** `usb_device` serves one interface to its class driver: Describe (its IDs, speed, class, and its
  endpoints), Control on the default endpoint (SET_ADDRESS, SET_CONFIGURATION and SET_INTERFACE refused, and
  requests only to the interface, its endpoints, or the device's descriptors and status), Transfer on its bulk and
  interrupt endpoints, one in flight on each, ResetEndpoint, and a buffer of its own as the block protocol's. A
  transfer crossing a 64 KiB boundary is two chained TRBs. `usb_bus` is what the driver tells the supervisor: each
  interface Attached, with a connection to it, then Settled once what was there at start is told, and Detached.
- **The supervisor** waits, after the boot set's drivers, for each host controller's Settled (10 s at most), keeping
  each interface and its connection; 20e starts class drivers for them. Until then it logs each as having none.
- **20c's empty controller, fixed**: on x86-64, q35's AHCI controller with only its CD made the supervisor start a
  storage manager with no disks, and a diskless boot degraded. The supervisor now asks each disk's driver its size
  first, giving the storage manager only disks with blocks, and starting none without one; the disk check also skips
  its partition test when the storage manager has no partitions. x86-64's boots start 9 services where AArch64's and
  RISC-V's start 8, the AHCI driver among them.
- **Test**: "finds USB devices on root ports and behind a hub", `qemu-xhci` with `usb-kbd`, `usb-hub` with `usb-mouse`
  behind it, and `usb-tablet`, on all three: each device's interface logged and Attached.
- **Kept for the end**: devices plugged in after start are addressed and Attached, but the input service and the
  storage manager take their devices only as they start, so one that comes later isn't given to them.

## As Built: 20e, USB keyboards and mice (2026-11-27)
- **USB class drivers in the system records**: a service's `usb`, a `UsbMatch` of class, subclass and protocol (either
  of the last two `USB_ANY`), kept in each record's `usb_class`, `usb_subclass`, `usb_protocol` and `usb_flags`, and
  checked as a driver is: the supervisor starts it, and it's no PCI driver too. The supervisor starts the first that
  matches each interface a host controller's driver Attached, with a connection to the interface (`UsbGrants`), into
  an entry of its own that speaks its protocol, so the input service takes it as it does any input device; a restart
  connects to the interface again.
- **`src/drivers/usb_hid`**, for class 3: a boot keyboard or mouse put in the boot protocol (SET_PROTOCOL), anything
  else, as QEMU's tablet, read through its report descriptor (its first report's buttons, X, Y and wheel, absolute or
  relative as it says, its logical range the input protocol's axes); SET_IDLE 0; one interrupt transfer always in
  flight, each report become events: a keyboard's modifiers and keys by their HID usages as they change, a pointer's
  buttons, motion or position, and wheel. Clients are served as virtio-input's are.
- **Budgets**: 2 MiB, as a log record with arguments needs heap and one that can't be put together is dropped
  silently, which 1 MiB made look like a hang; and no interactive CPU share, as the scheduler had none left to give.
- **`boot.py --input-bus=usb`** puts `--keyboard-input`'s keyboard, and `--display`'s tablet, on a `qemu-xhci`; a USB
  keyboard is typed 20 ms a key event apart, as QEMU's `usb-kbd` keeps only 16 events until the next report.
- **Tests**: "types on a USB keyboard into the console" and "moves the cursor with a USB tablet" on all three; the
  USB devices test now sees the keyboard, mouse and tablet served. A relative mouse is
  only seen served; nothing yet moves one.

## As Built: 20f, USB mass storage (2026-11-27)
- **`src/drivers/usb_storage`**, the class driver for mass storage's SCSI transparent command set over bulk-only
  transport (class 8, subclass 6, protocol 0x50), started by the supervisor as 20e starts HID's, its entry speaking the
  block protocol, so the storage manager takes it as any disk, and the first disk's if it's that. LUN 0 only (GET MAX
  LUN asked, a stall taken as one LUN); TEST UNIT READY until the disk's ready, REQUEST SENSE clearing each unit
  attention; READ CAPACITY (10), READ (10), WRITE (10) and SYNCHRONIZE CACHE (10) for Flush. A disk larger than 2 TiB
  of blocks would need the 16-byte commands, which aren't there.
- **One command at a time**, as bulk-only runs them: each request is waited for through its three stages before the
  next is taken. A stall on the data or status stage is cleared and the status read; a phase error or a status that
  doesn't check starts the reset recovery. Each client's buffer is ordinary memory, 32 KiB, copied to and from the
  interface's DMA buffer.
- **FAT's parser was fuzzed already** (`src/fat/test/fuzz_test.hsc`, design/storage.md §9: damaged boot sectors,
  FATs and directories, mounted and walked), and every FAT server runs untrusted; a stick's FAT volume is read the
  same way as any.
- **Tests**: "reads and writes a disk on a USB stick" (the disk check through it, its ESP's FAT32 through a FAT
  server) and "boots from a disk on a USB stick" (edk2 has USB storage on all three), each on all three. The root task
  has 110 grants.

## As Built: 20g, RISC-V's debug triggers (2026-11-27)
- **Through the SBI's debug triggers extension (DBTR)**, as supervisor mode can't reach Sdtrig's CSRs: probed at boot,
  how many address match (mcontrol6) and instruction count (icount) triggers a hart has logged, and **`RiscvSdtrig`**
  a new CPU feature (169) where it has address match triggers, which test_control asks for in place of skipping on
  RISC-V. Each slot is an mcontrol6 trigger for user mode, an Execute slot's on the instruction, a data slot's on its
  bytes by size; they're installed through the SBI as a debugged thread returns to user mode, from memory in the
  hart's ArchCpu (in the direct map, so its physical address is known), and uninstalled as it enters the kernel.
- **A trigger's breakpoint exception** is told from an ebreak by stval: a watched address that isn't the pc is a
  Watchpoint there, as QEMU reports the address a data trigger hit; else, stepping, a SingleStep.
- **A step without an icount trigger**: OpenSBI 1.8.1's DBTR gives none, and QEMU takes mcontrol6's not-equal match as
  equal, so a step is an execute trigger on each place the thread's instruction can go next: its successor, a jump's
  target (JAL, JALR, C.J, C.JR, C.JALR, a register's read from the thread's registers), or a branch's two.
  `arch_interface.set_debug` is given the instruction at the thread's pc, which the kernel reads from its memory; the
  other architectures ignore it. A step and its breakpoints share the hart's triggers, 2 on QEMU.
- **The shell's debugger** found a fiber pool through x28 on RISC-V, AArch64's carrier register; Hemera's on RISC-V is
  s11, x27, which it reads now.
- **Tests**: test_control's 8 now all pass on RISC-V (its breakpoint, step and watchpoint), and the shell debugger's
  three tests, left out of RISC-V until now, pass there. The ABI description has the new feature.

## As Built: 20h, an IMSIC in groups (2026-11-27)
- **Every `reg` range of the IMSIC is mapped**, up to 8 (one for each group), and each hart's supervisor file is found
  as Linux finds it: the files run on through the ranges in order, `interrupts-extended`'s order. Each file's number,
  which the APLIC's targets name it by, is its group (`riscv,group-index-bits` from `riscv,group-index-shift`) then its
  hart index (`riscv,hart-index-bits`), from its address, with the binding's defaults (no group bits, a shift of 24,
  as many hart bits as the files need). Boot logs the files and groups found.
- **The doorbell** (`arch_interface.MsiDoorbell`) has groups now: a run of pages for each, `group_stride` apart; L2
  maps each group's pages into a domain, reserving the span from the first to the last so nothing else is given those
  addresses. x86-64 has none and AArch64 one group; RISC-V's IOMMU with MRIFs uses its own window instead, so the
  grouped doorbell is for an IOMMU without them. MRIFs' notices go to each hart's file, as before.
- **Test**: "RISC-V: runs on harts in two IMSIC groups", virt with 4 harts on two NUMA nodes, as QEMU makes a socket
  of each: 4 files in 2 groups, and the system's services and devices' MSIs working across them.

## As Built: 20k, C-callable exports (2026-11-27)
- **Hemera had most of it**: a `.c` function with a context gets an entry shim, its symbol and value, which keeps the
  caller's carrier register, finds the thread's carrier block, runs the body with the foreign call's context, and puts
  the register back, on Windows x64 and Linux linking C; only functions so marked get it. What was missing was SlopOS.
- **On SlopOS**, each thread's thread pointer points at a word holding its carrier block, set by Hemera's runtime as the
  first thread and each thread starts (`runtime.register_carrier`), and the shim reads the word through it: `%fs:0`,
  or a load through `TPIDR_EL0` or `tp`. The kernel keeps a thread's pointer in its vector state, AArch64's
  `TPIDR_EL0` read as it's saved and both written as it's restored (x86-64's MSR only when it changes); RISC-V's `tp`
  is one of the saved registers already. x86-64's user mode can't write fs base (FSGSBASE would also let it write the
  GS base the kernel's per-CPU state is in), so it's set through a new system call, `thread_set_pointer` (99).
- **C in SlopOS's programs**: a program folder's `c/` sources are built by `tools/c_libraries.py`, with a stock clang
  as freestanding position-independent ELF, into `lib<program>_c.a` beside the programs, which every program has as a
  library path, so `#library("<program>_c")` links it; boot.py, the boot tests and the unit tests run it before the
  programs build. Visual Studio's clang has no RISC-V backend, so there it gives bitcode, which the `llc` of Hemera's
  LLVM compiles (kept for the end: a full LLVM release has every backend).
- **Test**: "calls back into Hemera from C, through the thread pointer", test_callbacks's C sorting by a Hemera
  comparison with the carrier register spoiled before each call, each callback allocating through its context, on
  all three. Hemera's own Linux test of `qsort` calling back stays as it was. The root task has 111 grants.

## As Built: 20i, indexes (2026-11-27)
- **In the volume's own tree** (`src/slopfs/index.hsc`), four new record kinds: a declaration, `(0, IndexDecl, n)`,
  the schema hash, the field's offset, size and kind, the value's fixed size and the field's name, worked out when
  it's declared, so the schema's bytes aren't kept; a bucket, `(INDEX_OBJECT_BASE | n, IndexEntry, key)`, the IDs of
  the files whose value has that key, `INDEX_OBJECT_BASE` being `1 << 63`, after every object; and each file's record
  of it, `(file, IndexedBy, n)`, its key and a text's first 255 bytes, which an update finds the old entry by and a
  query evaluates from. A key orders as the value: unsigned as it is, signed with its sign bit flipped, a bool 0 or 1,
  a text its first 8 bytes big-endian. So a commit makes a file's change and its entries together, `forget` undoes
  both, and a snapshot or a clone has the indexes its tree had.
- **A bucket holds 512 files**, a record's 4096 bytes of IDs; a file past them goes in a record of its own,
  `(INDEX_OBJECT_BASE | n, IndexSpill, file)`, holding its key, which queries walk after the buckets, so a bool's
  index of thousands of files works, at a record each past the 512th. The bucket holds no text: it's in each file's
  own record, which the design had in the bucket.
- **Declared through dir's `DeclareIndex`** on a writable directory, for its whole volume: the type's schema's bytes,
  whose hash the server works out (`schema.hash_rooted`), and the name of one of its root struct's own fields, an
  integer of 1 to 8 bytes, signed or not, little- or big-endian, a bool, or text, a `Relative` of one-byte elements.
  Anything else is `WrongType`; 64 indexes a volume (`NoSpace` past them); declaring one there is gives its number
  again. It's built at once from every file of the type, walking each object's record. `DropIndex` takes one out,
  its buckets and every file's record of it; `Indexes` lists them, with each field's name and kind. A connection
  reached through a stored link is `ReadOnly`; a transaction's is `Unsupported`. `Features.indexes` says so; FAT
  answers all three `Unsupported`.
- **Kept as each transaction commits**: the volume notes every object changed (`note_indexed`, from `note_change` so
  every create, write, cut, rename, removal and install, and from `destroy`, `set_schema` and the file an install
  orphans), up to 1024, past which every file is indexed again; `write_volume` indexes each again before it writes the
  tree, so every commit does, the container's own included. Its old entries are taken out by its own records, and it's
  put back if it's a file with a name (not an orphan), of a schema an index is of, whose value holds its fixed part,
  every indexed field inside it, a bool 0 or 1 and a text after the fixed part and inside the value: in every index of
  its schema, or none. A typed write committed half done, emptied and not yet written, isn't indexed until it's whole.
- **Left to decide**: an index that can't be updated at commit (no memory, no space for its nodes) fails the commit as
  a tree that can't be written does, and the volume's failed; and std's `schema.parse` calls the assertion handler
  without memory, the one place the volume server doesn't fail a request instead (decisions/0104).
- **The query engine came with it** (`src/slopfs/query.hsc`, 20j's), as the tests read the indexes through it.
  Hosted tests (`src/slopfs/test/index_test.hsc`): `an_index_is_built_from_what_is_there_and_refuses_what_it_cant_hold`,
  `an_index_follows_writes_renames_removals_and_replacements_as_they_commit` (an emptied value unindexed, and
  dropping), `a_bucket_full_of_one_value_spills_and_every_file_is_still_found` (1064 files, past the bucket and the
  changes noted) and `an_index_forgets_with_its_transaction_and_a_snapshot_keeps_its_own`.

## As Built: 20j, queries and live queries (2026-11-27)
- **A predicate** is postfix terms (std's `query` package, `Term`): comparisons (`=`, `≠`, `<`, `≤`, `>`, `≥`) of an
  index's field with a number or a text, and `And`, `Or`, `Not`, up to 32; a `Term` holds plain `u32`s, as a
  `Relative`'s items can't be enums, and its text is an offset into the predicate's texts. Every index it names has
  to be of one type (`WrongType` otherwise). A comparison at its top, or one arm of an and there, but not `≠`, bounds
  the walk to its index's range; otherwise the first index it names is walked whole. Each file walked is then tested
  against the whole predicate from its records of the indexes, without reading it, a text by its first 255 bytes.
- **dir's `Query`** answers the first file beneath the handle from a cursor (`Matched`: its path relative to the
  handle, its number, the next cursor; `End`), as `Changes` pages: a file beneath it (`is_beneath`), by its path from
  it (`path_to`, so one more than 16 levels down has an empty path). A file whose value changes between pages may be
  answered again or missed, as its key moves past the cursor.
- **dir's `LiveQuery`** opens a connection of its own, speaking `query`, as `Select` opens a set's: each `Next` is
  answered with `Matched` for each file that matches, then `Current`, then `Added`, `Changed` (a file still matching,
  written or renamed) or `Gone` as commits change them; a `Next` with nothing to answer is held, and answered by the
  commit that makes something. It keeps its members, up to 1024 (past them it ends, `NoSpace`), and the files each
  commit changed, up to 256; past those, or a commit that changed more than the volume noted, or moved a directory, it
  answers `Resync` and begins again. 8 live queries a server. They're evaluated from the indexes, so they see what's
  committed.
- **std's typed API** (`std/os/slop_os_queries.hsc`): `declare_index[T]`, `index_of[T]`, `where_number[T]` and
  `where_text[T]` (a comparison from a field's name and a value), `both`, `either`, `negate`, `query_in` (every page),
  and `open_live_query`, `next_live_event` (with a deadline) and `close_live_query`.
- **The shell's `query`**: `query Note level >= 3 and title != draft` lists the typed files beneath its directory as a
  table of `path` and `file`, the type found by its name among the programs' manifests, as `view` finds a typed file's,
  and each field's index by listing them; `query --index Note level` declares one. Comparisons are joined by `and`
  alone, as `or` is the shell's own keyword, and there's no `not`; `Query` itself has both.
- **Left out**: `Query` and `LiveQuery` on `read_only_dir`, so a snapshot's indexes, which slopfs queries (its tests
  do), aren't asked through the protocol.
- **Test**: disk_check's `indexes_answer_queries_and_live_queries_follow_commits` (`query_check.hsc`), on the system
  volume: two indexes declared, typed notes written and committed, queried by a comparison and by an and of two, and a
  live query that answers the two that match, then a note added and one removed as each commits. disk_check has 14
  tests.
